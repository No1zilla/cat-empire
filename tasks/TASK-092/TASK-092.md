## Как нашли

В `ads.recent` на дашборде видны пары с точностью до миллисекунды:

```
19:51:29.966  ad_failed     reward_gems  NO_ADS  reward
19:51:29.966  ad_requested  reward_gems
19:51:29.966  ad_failed     reward_gems  NO_ADS  reward   ← дубль
19:51:29.966  ad_requested  reward_gems                    ← дубль
```

В `09:14:56.331` — сразу по четыре на разные `ad_type`.

Ключ к разгадке: `timestamp` ставится при **создании** события. Два разных клика не попали бы в одну миллисекунду. Значит это не двойной клик, а **одно событие, доставленное дважды**. Проверка подтвердила: `HUD._draw()` зовётся один раз и начинается с `removeChildren()`, слушатели не копятся.

## Причина

Доставка была «хотя бы раз», а дедупликации не существовало:

1. **`flushSync()`** ([`EventTracker.js`](../../src/analytics/EventTracker.js)) шлёт очередь маячком на `visibilitychange`/`pagehide` и **никогда её не чистит** — ни `queue = []`, ни оглядки на `isFlushing`. События уезжают маячком, а потом ещё раз обычным `flush()`.
2. **`flush()`** обрезает очередь только **после** ответа сервера. Если сервер записал батч, а ответ не дошёл (сеть моргнула, `keepalive`), клиент отправит всё заново.
3. У событий не было уникального id — сервер физически не мог отличить повтор.

### Вторая течь, серьёзнее

`session_start` при каждой доставке инкрементил `session_count` и двигал retention-флаги ([`events.js`](../../server/src/routes/events.js)). Отсюда `total_sessions_today: 23` при `dau_today: 2` и `avg_sessions_per_dau: 4`.

То есть завышены не только счётчики рекламы, но и **сессии, и D1/D7**.

## Решение

Дедупликация по уникальному `event_id` — так «хотя бы раз» превращается в «ровно один раз», и чинить `flushSync` не нужно: повторы просто отсекаются, а события при этом не теряются.

- **Клиент**: `_generateEventId()` на каждое событие в `track()`
- **БД**: колонка `event_id` + **частичный** уникальный индекс `WHERE event_id IS NOT NULL`
- **Сервер**: `ON CONFLICT (event_id) WHERE event_id IS NOT NULL DO NOTHING RETURNING id`; пустой `RETURNING` = дубль → `continue`, счётчики сессий не трогаем
- Ответ отдаёт `{ count, duplicates }` — сколько повторов погасили

Индекс частичный намеренно: у старых закешированных клиентов `event_id` нет, они пишутся как раньше (в SQL несколько `NULL` уникальность не нарушают).

### Защита от собственной миграции

Миграция в `db.js` — best-effort (`try/catch` + warn). Если бы она не прошла, `ON CONFLICT` свалил бы **каждый** insert → rollback → аналитика умерла бы целиком.

Поэтому `canDedupe()` один раз проверяет наличие индекса в `pg_indexes` **до** `BEGIN` и при отсутствии откатывается на обычный insert. Проверять внутри цикла нельзя: упавший statement в Postgres отравляет транзакцию целиком.

## Проверка на живом Postgres 16

Локального сервера не было, поднимали одноразовый в Docker:

| Шаг | Результат |
|---|---|
| Миграция (`ALTER` + частичный индекс) | прошла |
| Проба `canDedupe()` | нашла индекс |
| Первая доставка | `INSERT 0 1` |
| **Повтор того же `event_id`** | **`INSERT 0 0`** — погашен |
| Старый клиент (`event_id = NULL`) ×2 | обе записались |
| Итог | `ad_failed` = 1, `legacy` = 2 |

## Важно для чтения старых данных

Дедупликация действует **вперёд**. Всё, что уже записано (включая цифры в [TASK-083](../TASK-083/TASK-083.md)), содержит дубли. Абсолютные значения оттуда занижают fill rate и завышают сессии; соотношения причин отказа при этом остаются осмысленными, если дубли распределены равномерно.
